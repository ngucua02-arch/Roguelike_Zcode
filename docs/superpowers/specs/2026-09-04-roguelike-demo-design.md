## 1. 概述与目标

做一个**传统回合制地牢爬行 roguelike 的可玩 demo**：网格地图、回合制移动与战斗、程序生成地牢、逐层递进、死亡重开。2D 像素风。

**成功标准**（demo 完成的定义）：

- 一局完整体验：随机生成地牢 → 探索 → 战斗 → 捡道具 → 下楼梯 → 3 层后通关或中途死亡 → 结算画面 → 重开。
- 纯鼠标键盘本地运行（Windows），可导出 Windows exe 与网页版分享。
- 玩法规则层全部有单元测试，改数值不碰代码、改渲染不崩逻辑。

## 2. 范围

**做（demo 内）**：

- 1 个玩家职业；3 层程序生成地牢；4-5 种怪物；5-6 种道具（药水、武器、护甲类）。
- 回合制战斗（近战、相邻格攻击）、简易视野迷雾、经验升级、消息日志、HUD、背包界面、主菜单、死亡/通关结算。
- Windows + Web 两个导出目标。

**不做（明确排除）**：

- 在线多人、账号、云存档。
- 复杂 AI（寻路用贪心逼近即可，不做 A* 优化）、状态效果系统（中毒/眩晕等留到正式版）。
- 存档系统（短局 + 死亡重开即 roguelike 本味；如后期想要，列为 M5 可选项，用 Godot `user://` 存档）。
- 音效为可选项，不阻塞 demo 完成。

## 3. 技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 引擎 | Godot 4.x 标准版（非 .NET 版） | 用户选择借 demo 上手套件；Windows 绿色单 exe 免安装 |
| 脚本语言 | GDScript | demo 迭代最快、Godot 原生；C# 需额外 .NET 环境不值得 |
| 架构原则 | 核心规则写成**不依赖场景树的纯 GDScript 类**，节点只是表现层 | 承重墙：规则层可被 GUT 单元测试；渲染与玩法互不牵连 |
| 地图渲染 | TileMapLayer + 运行时生成的 TileSet | Godot 4.3+ 标准做法 |
| 移动表现 | 逻辑瞬间结算，Tween 补间做平滑走位 | 回合制无需物理引擎 |
| 数值内容 | 自定义 Resource（.tres）：MonsterDef / ItemDef / FloorDef | 编辑器面板可改数值，不碰代码 |
| 测试 | GUT 插件，覆盖 `src/core/` 全部 | 延续既有项目"规则层全测试"习惯 |
| 视野 | 先做 Bresenham 射线简易 LOS，不够再升级阴影投射 | YAGNI |
| 素材 | 三步走：色块占位 → Kenney CC0 像素包 → 自绘替换 | 保证任何时刻都"可玩"，美术板块可整体替换 |

## 4. 架构

### 4.1 分层

```
┌─ UI 层（Control 节点）：HUD、日志、背包、菜单、结算
├─ 渲染层（Node2D）：TileMapLayer 同步器、实体精灵、镜头、Tween 动画
├─ 调度层：TurnManager（Autoload 单例）——接收输入 → 调规则层 → 把事件广播给渲染/UI
└─ 规则层（纯 GDScript，无场景依赖，GUT 全测）
    DungeonModel · DungeonGenerator · TurnScheduler · Combat · FOV · 事件流
```

数据流：玩家按键 → `TurnManager` → `TurnScheduler.player_action(action)` → 规则层瞬间结算并返回**事件列表**（移动/攻击/死亡/拾取/下楼梯…）→ `TurnManager` 把事件分发给渲染层（Tween 播放动画）与 UI 层（写日志、刷 HUD）。渲染层不修改规则层状态。

### 4.2 规则层接口（要点）

- `DungeonModel`：网格尺寸、瓦片枚举（墙/地/门/楼梯）、实体容器、玩家坐标；提供 `is_walkable(pos)`、`entity_at(pos)` 等查询。不持有任何 Node 引用。
- `DungeonGenerator.generate(floor_def) -> DungeonModel`：随机房间 + 走廊连接；保证从入口到楼梯连通；首个怪物/物品/楼梯/玩家出生点按 FloorDef 撒点。
- `TurnScheduler`：玩家行动 → 遍历怪物行动（AI：视野内贪心逼近，视野外随机游走）→ 返回本轮事件列表。
- `Combat.attack(attacker, defender) -> events`：伤害 = 攻击力 - 防御力（最小 1），死亡产生死亡事件与经验事件；经验满升级。
- `FOV.compute(model, radius) -> 可见格集合`：以玩家为中心 Bresenham 射线。
- 事件流：简单字典数组 `{type, pos, data}`，渲染/UI 按类型消费。

### 4.3 数据（.tres 资源表）

- `MonsterDef`：id、名称、hp、atk、def、视野半径、经验值、精灵帧、AI 类型。
- `ItemDef`：id、名称、类型（药水/武器/护甲）、效果数值、图标。
- `FloorDef`：层数、地图尺寸、房间数范围、怪物表（id+权重）、物品表、楼层主题色。
- 玩家初始数值与升级曲线写在一个 `PlayerDef` 资源里，同走数据表。

### 4.4 工程结构

```

├── project.godot          # 输入映射（方向键/WASD/空格）、像素渲染设置
```

### 4.5 像素渲染与操作约定

- 16×16 瓦片；项目纹理过滤设为 Nearest；窗口用 `viewport` 拉伸模式保持整数缩放，避免像素抖动。
- 移动：方向键或 WASD，八方向简化为四方向（上下左右）。
- 拾取：走到物品格**自动拾取**；背包内用鼠标点击使用/装备。
- 下楼梯：站在楼梯格上按空格/回车确认下楼。
- 怪物行为约定：玩家进入怪物视野半径即进入追击状态（贪心逼近），脱离视野后随机游走；不追跨楼层。
- 地牢默认规模约 40×25 格、每层 6-9 个房间，具体由 FloorDef 数据表控制。

## 7. 测试策略

- 规则层（`src/core/`）全部 GUT 单元测试：生成器（房间不重叠、全连通、楼梯可达）、战斗数值（含最小 1 伤害边界）、调度顺序（玩家→怪物、死亡不再行动）、FOV（墙挡视线）。
- 生成器用固定随机种子做确定性测试。
- 表现层（渲染/动画/UI）以人工试玩验收为主，不写自动化。
